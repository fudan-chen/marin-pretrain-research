18T尺度下的混合计数：溢出风险与Hero配置的实际边界

归档MixtureDataset有一条可复现的整数溢出路径：每块计数和跨阶段累计量都使用int32，乘法或累计超过2,147,483,647后可能回绕；之后转成Python int无法恢复。有限数据集的restart取模还可能把错误的负索引变成合法索引，使训练继续读到另一个样本。

这不是Hero已发生事故的证据。 V36本地计算的归档三阶段配置下，18T目标约对应43.96亿序列，单桶累计上界约2.57亿，低于int32限制；V89发现该取整结果依赖Python浮点求和语义，不能直接代填生产配额。必须按“每个实际混合组件”检查，而不是拿总序列数直接判故障。

本章依据固定源码、归档配置和22项原函数检查。原函数用真实NumPy 2.0.2执行，人工对象替代dataset和初始化依赖；没有模拟掉整数运算。未执行JAX、真实DataLoader、token流、GPU或历史事故重放；Hero当时的NumPy版本仍未知。

2. 负索引为何可以悄悄变成正常样本

用生产同样的block_size=49,152，但人工设置只有一个数据组件，每块全部来自A。第43,691块的预期组件起始索引是2,147,500,032，刚超过int32上限。这个序列索引并不需要分配几十亿样本：探针只构造一个块及少量计数，再直接调用索引方法。

人工对照 得到的数值 含义
Python整数独立计算 2,147,500,032 正确逻辑索引
原跨阶段累计结果 −2,147,467,264 比正确值少2³²
原Python-int当前阶段路径 −2,147,467,264 乘法完成后再int转换仍错误

_remap_indices对有限数据集的restart/all_exhausted执行 idx % length。负数取模落到0..length−1，所以“索引没有越界”和“继续训练时loss有限”都不能证明数据游标正确。若数据集长度恰好使2³²取模为0，某些错误映射还可能碰巧相同；本例证明存在错误读取路径，不声称所有长度都必然改变样本。

实际dataset键顺序未取回。本次按权重声明构造200个活跃组件，三个阶段分配余数的最大计数桶均唯一，计数不依赖平局裁决顺序；没有证明历史dataset集合、文件内容与该声明完全一致。零权重、微小正权重被截成0的情况仍保留在原值账本中。各阶段分别有17、0、1个正权重组件的整块计数为0，提醒读者权重声明与曝光仍须分开；不能将这些数字当作已重放的实际样本。

这也给迁移配方一个具体提醒：把200桶改成更粗的域、连续做高比例CPT、增加训练预算，都可能把原先分散的计数集中到少数组件。检查应重新执行，不应沿用“Hero用过这段代码”的判断。

4. 修复候选与验收边界

三处候选补丁仅用于本地审查，未修改源归档、未提交上游、未在训练环境应用：

  1. 跨阶段累计数组改为int64。
  2. 单阶段乘法之前将每块计数提升到int64。
  3. 当前阶段标量乘法之前转为Python整数。

探针执行这三处改动后的方法，核对两个溢出例、当前阶段索引、原小索引行为，以及每块计数仍保持int32。它没有把所有计数类型一起改掉，也没有改变配比、块内置换或随机key。int64也有上限，任意超大输入仍需Python整数预检。

真实修复验收至少应覆盖：生产NumPy版本；Python int/np.int64两种入口；多阶段累加；有限数据集取模；同key下修改前后正常范围token流一致；阈值附近修复后与独立整数参考一致。当前只完成前述CPU计数和映射检查，真实token流与分布式读取未完成。

可重跑：

.venv/bin/python scripts/probe_mixture_range.py

本章给配比管线增加一个具体的检查入口：先计算每个组件在所有阶段的计数上界，再检查每一步中间乘法的类型；不能只检查最终结果或总token预算。 在恢复和配比收益归因之前，把它与batch前缀、缓存身份、真实cursor共同核对，避免将读取变化解释成训练策略收益。

怎样调整配比才会真正改变曝光

先将候选weight编译成每块整数计数，与基线逐桶比较；记录零支持、接收余数的桶以及所有被连带改变的供体。调整一个微小桶而其整数计数不变，在这份确定块算法下不会改变完整块域配额。实验应以实际整数交换量定义预算，连续weight保留为设计目标；研究顺序时还要匹配末块和域内库存身份。

本轮外部累计采用int64，避免把计数审计本身引入V36的int32溢出；原每块计数仍保持原dtype。没有执行原跨阶段累计或索引读取，不能用本次安全累计证明原整体实现安全。新增1份同head完整源码，495份旧非bookkeeping来源字节保持，来源共497份。获取台账。复现：make integer-exposure-cpu CPU_PYTHON=/tmp/marin-jax-cpu-072/bin/python。

V89：Python求和的一点误差，怎样变成184个桶的整数差异

V88保留了来源差异，却没有解释旧结果为何不同。本轮在两份实际环境执行同版原_normalize_weights与原块配额函数：Python 3.9.6 / NumPy 2.0.2，Python 3.12.13 / NumPy 2.5.3。三份输入分别是同head spec、历史W&B配置、10月7日W&B归档；每份均测试native sum、顺序求和控制与math.fsum控制。两环境各27格、54项守恒/独立整数参考检查，另有7项跨环境对照。没有执行完整数据加载器或生产环境。

Python 3.12官方文档说明浮点sum在3.12更换了提高精度的算法。本例cooldown权重在3.9 native sum为1.0000000000000002，在3.12 native sum为1.0。原归一化将每桶除以这个值；许多weight×49152本来就在整数门槛上，稍微减小后被int32赋值截成前一个整数。随后余数全部归最大桶，错误/差异既减少许多桶，又集中增加一个桶。

如何排除NumPy版本这个混杂因素

两环境的NumPy版本不同，直接看到quota不同仍不能只归因Python。本轮在同一原函数体中，仅替换全局sum依赖：明确逐项累加的控制在两环境输出全部一致，math.fsum控制也全部一致。每格还用独立Python int截断与余数计算核对原NumPy赋值结果，均匹配。3.9 native在本例对应顺序控制，3.12 native对应fsum控制。这些控制把差异定位到求和→归一化→取整链；替换依赖是诊断控制，没有改动上游，不能称作经过训练验证的修复。

V36原JSON记录了NumPy 2.0.2，未记录Python版本。本轮3.9控制重现其cooldown计数，因此旧数值应按本地运行时结果阅读，不能断言原始执行Python二进制已经独立恢复。10月7日W&B元数据声明Python 3.12.14，本轮使用3.12.13；这个声明与3.12算法说明有参考价值，但没有取回生产二进制、实际组件树或原始已编译quota。不能因此将本地3.12计数直接命名为真实Hero曝光。

给自己的预训练管线的规则

配置身份应同时包含输入float十六进制值、键顺序、Python/NumPy版本、归一化算法以及最后的整数quota，而非仅有JSON文本或“比例和接近1”。复现已有训练时，先核对共同阶段的整数向量；若要改变归一化实现，应作为会改变数据映射的迁移验收，检查域内cursor与恢复前缀。

新管线可以显式保存整数配额并审查其预算，避免每次运行临时重算；也可研究稳定求和与明确的取整政策。但这些是设计建议，本轮没有比较其训练收益，不建议给所有weight随意加epsilon来掩盖门槛。源码没有改动，输入与输出原值见3.9记录和3.12记录。新增官方文档归档1份，旧496份非bookkeeping来源字节保持，来源498份。

单条路径以Python整数生成block_id，offset乘np.int32配额时结果仍可能在窄类型内计算；批量路径先把block_ids放进NumPy数组，本轮得到np.int64，当前阶段乘法保持宽类型。因此，“只测一种取数接口”会遗漏另一种行为。这里结论绑定Python3.12.13 / NumPy2.5.3；真实调用方传入的类型和依赖版本也需保存。

跨阶段控制更说明接口一致性不够。原构造器用int32的counts_this_stage乘阶段块数，初始阶段累计2,147,483,648条变为−2,147,483,648。后续两条读取路径都加这个坏base_offset，随后restart取模映射到合法库存身份A:319。没有越界错误，返回也不是NaN，但数据身份已经改变。共同错误前缀能使两个API互相通过，必须另有宽整数参考与内容/身份核对。

更大Python块数在本轮运行时还会触发“Python integer out of bounds for int32”的OverflowError。不要把不同失败机制合并成“所有大计数都会静默溢出”。本轮直接保留三种原结果：接口分歧、共同错误、构造拒绝。13项原构造/读取CPU控制 · 复现脚本

同时把反例放回Hero声明范围

从10月7日归档读取constant train_batch_size=11264、num_train_steps=390251、block_size=49152，将三阶段声明位置换算为0、1,216,512,000、3,516,530,688条序列。它是声明恒定batch控制，不是实际历史loader复原。原构造器保留200个正支持桶；前两阶段原int32累计向量的全部200项，分别与独立Python整数累计完全一致，最大prefix为60,835,500和173,562,246。

终点全局序列预算4,395,787,264超过int32，但这不是每个子域的计数。把最后不足一块按完整块纳入保守上界，逐桶最大计数为253,722,855，仍低于2,147,483,647。它绑定本轮运行时归一化和原配额，不能替换V36的历史本地上界，也不能称为实际曝光。六个读取点为起点、两阶段边界前后与预算最后一槽，使用人工1009库存，单条/批量均与独立索引算术匹配。六点没有证明所有真实token、缓存和恢复路径正确。

结论应精确到条件：原接口风险已在人工集中配额下端到端复现；归档Hero的本地逐桶上界不满足该反例的溢出条件。新增CPT预算、合并数据桶、集中权重或重新设定阶段以后，应按新配额重检，不能搬用这个上界。

修复原则仍是把类型提升放在乘法和累加之前：阶段产品、跨阶段累计、当前阶段offset三处分别处理；最终再int转换无法恢复已经溢出的值。应保留单条/批量共同位置的对照，同时加入独立宽整数参考，检查restart前的原始域内索引与取模后身份。本轮没有修改上游，也没有以人工正确读数宣称训练收益。

V128：桶级权重的数值合同

权重范围检查增加逐项有限性与总和有限性。两个有限大正数仍可让直接总和溢出；合法历史保留组件后，空/全零阶段的余数政策可把整块给首桶。正权重、归一化正支持与整数正曝光需分别记录；最小有限性保护未解决下溢或零整数配额。13控制、真实声明回归与未知。
