配比权重的数值合同：为什么坏阶段有时不会报错

“权重都是正数”“配置能够创建”“最终配额加起来等于块大小”是三项不同的检查。历史混合器会归一化权重、过滤不活跃组件，再把整数余数补给最大桶。几步各自看起来合理，组合后却存在这样的局部路径：后续阶段归一化为空或全零，但历史阶段保留了组件；余数补偿把整个块分给第一个组件，训练数据读取仍然成功。

本章用上传原类体执行该路径，补充配置启动与数据配比评审规则。例子使用人工身份。本轮核对的两份小规模实验归档声明没有NaN或求和溢出，535B历史与当前运行是否触发仍未知；没有据此估计loss、能力或故障频率。

本章weight是桶级采样权重；token级目标权重的非有限值传播另见零权重数值分析。

一、具体查了哪些代码

历史MixtureDataset._normalize_weights第173行起先计算sum(weights.values())，仅明确拒绝总和为0及负权重；对正权重计算weight / total，其他权重不放进输出字典。构造器按所有阶段归一化后的正支持并集保留组件。

第141行起的块配额方法将weight × block_size写入整数数组；随后找最大整数桶，将“块大小−配额总和”的余数全部补给它。全部整数为0时，最大值并列，argmax选择第一个位置。因此，正常情况下用于取整的余数逻辑，也可能接管一个已经失效的阶段。

执行完整历史类体与原LmDataConfig.__post_init__方法，使用上一章同样的依赖适配；两个严格有限子集A/B各有100条人工身份。采用Python 3.12.13、JAX 0.11.0 CPU、块大小8、不随机化块内排列；编译级别为0，不依赖上一章的assert移除。原值还包含两个真实归档配方的全部五份阶段权重。探针、13项控制与原值

这里没有执行完整配置解析器或训练入口。原初始化方法允许这些键合法的数值例子通过，不等于所有外层解析器都必然接受它们；模型、真实缓存和loss均未执行。

二、空阶段如何变成整块A

先给一个合法阶段A:B=1:1，在槽8切换到只有B=NaN的阶段。原方法产生：

阶段0：归一化 A=0.5，B=0.5 → 保留A/B → 配额 A4/B4
阶段1：总和NaN；NaN既不小于0也不大于0 → 输出空字典
       历史阶段已保留A/B → 整数初值 A0/B0
       余数8补给第一个最大桶A → 实际配额 A8/B0

实际读取的前16槽为A:0…3、B:0…3、A:4…11。坏阶段没有拒绝启动，也没有得到一个空batch；它拿到了完整的8条A身份。

将实际子集构造顺序从A/B改成B/A，坏阶段配额变成B8/A0。NaN没有表达任何有效目标比例；接收整块的域由插入顺序决定。这是非有限数值进入归一化后与余数政策相互作用的结果，不能解释成某种合理的数据回退策略。

若同一个NaN-only权重字典单独构造为唯一阶段，归一化后没有历史正支持，组件会被全部过滤，随后在空数组argmax处报ValueError。单阶段能够报错，不证明多阶段的相同数值输入也会被拒绝。 用只有一份普通配方的测试覆盖阶段配比，并不充分。

三、输入逐项有限，也不够

将后续阶段改成A=1e308, B=1e308。两个输入都是有限正数，但本运行时直接求和得到正无穷；两个归一化值变成0。历史仍保留A/B，原余数补偿再次得到A8/B0，反转子集顺序则得到B8/A0。

数学上，这组数仍表达1:1相对比例；该浮点实现却无法用有限分母表达其总和。需要同时校验每一项与实际求出的总和。只用sum > 0会放过正无穷，只检查weight < 0也无法排除NaN。Python的有限性检查定义明确将NaN和无穷值排除。

这不意味着真实配方通常会接近1e308。该反例用来验证接口的数值合同；真实归档的五份阶段权重范围正常，见后文。也不能由此推断所有包含无穷值的输入都会静默接受：本轮A=1, B=inf的静态与后续阶段例子均在后续运算报ValueError。

数值输入及上下文 原实现的实际结果 需要学到什么
负权重或总和为0 ValueError 已有拒绝路径，不能宣称毫无校验
NaN-only，唯一阶段 后续空数组argmax报ValueError 失败位置晚，错误原因不直接
NaN-only，合法历史后的阶段 接受；整块给第一个历史保留桶 阶段上下文影响失败方式
两项1e308，唯一阶段 后续空数组argmax报ValueError 逐项有限不能保证总和有限
两项1e308，合法历史后的阶段 接受；整块给第一个历史保留桶 余数守恒掩盖归一化失效
正无穷加有限正权重 本次静态/后续阶段均报ValueError 非有限输入不是一律同一种行为
A=1e-320，B=1 保留A/B；A整数配额0并warning 正支持与实际曝光不同
A=1e-300，B=1e300 A归一化下溢为0；Mixture中只保留B 归一化支持与原正支持也可不同

最后两行是不同层次的问题。1e-320仍能以本运行时浮点数表示，但乘8之后的整数配额为0；1e-300/1e300则在浮点归一化时已经变成0。不能把二者都叫“有一点小误差”，也不能用补一个epsilon保证实验预算正确。后者只证明Mixture内部的组件过滤，不证明上游train_sets的shuffle key被重新分配。

四、最小候选保护：拒绝失效输入，保留现有正常算术

本轮候选在调用原归一化前增加两道显式检查：所有输入有限；按原顺序求出的总和有限且大于0。随后仍调用原函数，保留其负权重拒绝、归一化与余数政策。

if not all(math.isfinite(v) for v in weights.values()):
    raise ValueError("All weight values must be finite")
total = sum(weights.values())
if not math.isfinite(total) or total <= 0:
    raise ValueError("Weight sum must be positive and finite")
# 继续调用原归一化；不要在这里悄悄换求和或取整算法。

候选拒绝了本轮八种异常输入，包括两个静默后续阶段；普通1:1与两种极小权重例子的原轨迹保持。它没有修复归一化下溢或整数零曝光，这两种行为需另设明确政策。当前是局部wrapper控制，未修改归档源码、上游实现或生产入口。

也可以研究先按最大值缩放再归一化，以支持更宽的输入动态范围。但那是另一种算法，仍需处理下溢和整数预算。V89已经证明，求和与归一化的末位变化能改变大量桶的整数配额；因此“更稳定”不能自动等同“恢复时数据位置不变”。归一化运行时差异

这五份声明没有触发本轮NaN或求和溢出条件。只能说明新增前置保护在这些输入上不改变所比较的字典和整数向量；不能代替完整历史环境、真实数据读取或模型恢复验收。

六、落到自己的启动预检与配比实验

  1. 保存原始权重、顺序和float.hex，检查逐项有限非负及实际总和有限正数；报错写明run、阶段、桶名和输入来源。失效配方应拒绝，不自动删坏桶后重新分配预算。
  2. 分别列出原正支持、归一化正支持和整数正曝光支持。支持缩小发生在哪一步，决定该查数值范围、取整政策还是组件构造；三者不能共用“桶数”字段。
  3. 整数向量之和等于块大小只是守恒检查，还需核对每桶预算与最大余数接收者。本例全量误分仍完全守恒。
  4. 多阶段测试同时包含合法历史之后的坏阶段、插入顺序反转和真实声明回归。一个单阶段报错例子不能证明整条阶段管线已保护。
  5. 修复数值合同与改变配方分开评审。前置拒绝检查可以争取保持正常算术；新的归一化、保底配额或重分配政策应按输入干预迁移，重新验收预算与恢复位置。

这组规则约束的是能否相信“配置比例→实际曝光”的映射，不直接推荐数学、代码或高质量桶的最佳占比。
